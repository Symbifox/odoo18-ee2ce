# Architecture

## The problem

An Odoo 18 Enterprise SaaS dump is a `pg_dump --format=plain` export with two parts:

1. **DDL** — `CREATE TABLE`, indexes, constraints, sequences
2. **Data** — `COPY ... FROM stdin` blocks (one per non-empty table)

You'd think `psql -f dump.sql` into a fresh DB would work. It doesn't, for many overlapping reasons:

- **Module metadata mismatch.** `ir_module_module` lists Enterprise modules (`account_accountant`, `web_studio`, `documents`, `sign`, ...) that aren't installed on Community. `ir_ui_view` references views from those modules. `ir_model_data` has xml_ids pointing to Enterprise records.
- **Enterprise-only columns.** Tables like `res_partner`, `account_move`, `project_task` have extra columns in Enterprise (`industry_id`, `payment_state`, `enterprise_specific_field`, etc.) that don't exist in Community. The DDL fails or the data fails.
- **Schema drift between SaaS builds.** Enterprise SaaS gets continuous deployment, so even within "18.0" the schema can have columns Community doesn't, and vice versa.
- **Reference data conflicts.** `res_country` and similar tables are seeded by base module CSV/XML data, with deterministic xml_ids. Importing Enterprise's version overwrites the Community-seeded rows but leaves dangling xml_ids.

## The two approaches I tried

### v1 — Full-dump import + metadata patching (abandoned)

The first attempt was: load the entire dump into a target DB, then run scripts to patch metadata afterward. This meant:

- Filter `ir_module_module` to mark Enterprise-only modules as uninstalled
- Delete xml_ids referencing Enterprise modules from `ir_model_data`
- Map Enterprise data tables to OCA equivalents (e.g., `helpdesk_ticket` → `helpdesk_mgmt.ticket`) field by field
- Fix sequences, FK orphans, CHECK constraints

This grew to 2,000+ lines and **never reached a stable state**. Every time one bug was fixed, two more appeared. The fundamental issue: Enterprise metadata is pervasive and nondeterministic — any patch leaves footprints that surface elsewhere.

### v2 — Fresh init + business data injection (this tool)

The current approach inverts the strategy:

1. **Drop the target DB entirely.**
2. **Let Odoo create it from scratch** with Community modules installed (`odoo -d <db> -i base,account,...`). All metadata — `ir_model`, `ir_ui_view`, `ir_model_data`, `res_groups`, `mail_template`, etc. — is generated by Community module code, with correct xml_ids.
3. **Import only data tables**, with column intersection filtering. Enterprise-only columns are silently dropped per row.
4. **Skip framework tables entirely.** They're already correct; touching them would re-create v1's problem.

The win is that the new DB **looks identical to one that was always Community**. No patching needed. Open it in Odoo, log in with your old admin password, and your data is there.

## Why column intersection works

`pg_dump` formats `COPY` blocks like this:

```
COPY public.res_partner (id, name, email, industry_id, x_studio_segment, ...) FROM stdin;
1   ACME   contact@acme.com   23   premium   ...
\.
```

The header lists Enterprise columns. The data rows are tab-separated, in the same order.

The importer:

1. Reads the header → list of Enterprise column names
2. Queries the target Community DB for that table's columns
3. Computes the **intersection**
4. For each data row, keeps only the fields whose column is in the intersection
5. Streams the filtered data through `COPY ... FROM STDIN` via psycopg2

Enterprise-only columns drop out. Community-only columns receive their schema defaults (or trigger `NOT_NULL_FIXUPS`).

## Why `session_replication_role = 'replica'`

Importing rows with FKs in arbitrary order would fail half the time (child before parent). Setting `session_replication_role = 'replica'` disables FK triggers for the session, letting the data load complete, after which the row counts pass FK checks because the dump itself is FK-consistent.

**Caveat**: this disables FK triggers but **not** `NOT NULL` or `CHECK` constraints. Those need explicit handling — that's why `NOT_NULL_FIXUPS` and the relaxed import path exist.

## Why never `TRUNCATE ... CASCADE`

`TRUNCATE x CASCADE` follows every FK from `x` to other tables and truncates them too — and onward to their children. On an Odoo schema this can wipe the entire database in one statement. The importer uses `DELETE FROM x` (no cascade) before each table's `COPY` to clear seed rows; if the seeded data has FK children, the delete fails and is rolled back, which is the right behavior.

## Phases

| Phase | Module | Purpose |
|-------|--------|---------|
| 0 | `cli.py` (inline) | Drop target DB, run `odoo -i` to init |
| 1 | `parser.py` | Single-pass scan of `dump.sql` for COPY blocks |
| 2 | `cli.py` (inline) | psycopg2 connection, target table catalog |
| 3 | `cli.py` (inline) | Plan: skip vs no_match vs import |
| 4 | `importer.py` | `import_table` (normal) / `import_table_relaxed` (NOT NULL fixups) |
| 5 | `sequences.py` | Reset every sequence to `max(linked_column)` |
| 6 | `filestore.py` | `tar | docker exec ... tar -xf` into `/var/lib/odoo/filestore/<db>` |
| 7 | `neutralize.py` | Disable mail, regen UUID, fix `web.base.url`, ensure `mail_alias_domain` |
| 8 | `verify.py` | Row counts (optional vs expected_counts) |

## What's not handled (and why)

- **Studio fields** (`x_studio_*`). These are dynamically created via `ir_model_fields` records in Enterprise. Without that table imported, the columns exist in the dump but the Community schema doesn't have them — they're dropped by the column intersection. To preserve, port Studio definitions to a Community module like [bf_studio_light](https://github.com/bluefoxconsultant/odoo-modules/tree/main/bf_studio_light) before migration.
- **Helpdesk Enterprise → OCA helpdesk_mgmt mapping.** v1 had a per-field mapping; the schemas diverge enough that data quality was poor. v2 punts: tickets are recreated manually, or the user installs the [Enterprise helpdesk OCA reimplementation](https://github.com/OCA/helpdesk).
- **Sign / Documents / Knowledge / Planning data.** No Community equivalent. Data is skipped.
